Running ComfyUI inference at scale on RunPod serverless

How I structured a GPU inference fleet for video and image generation — cold starts, model preloading, and fleet-wide Docker image management.

April 28, 2026

Open in harness → /?read=runpod-serverless-comfyui

The setup

Cinématique runs ComfyUI-based pipelines for video and image generation. Models include Wan2.2-Animate 14B, ViTPose, YOLOv10, and SeC-4B. The requirement: serverless GPU workers that scale to zero, spin up fast, and stay cheap.

RunPod Serverless was the right call. But the default experience — Docker image pulls model files at container start — produces cold starts measured in minutes for 14B models. That’s not acceptable for a production pipeline.

The cold start problem

A naive worker image does this on startup:

FROM nvidia/cuda:12.1-runtime
RUN pip install comfyui ...
CMD ["python", "start.py"]

And start.py downloads the model from HuggingFace before it can serve a request. First request latency: 8–12 minutes for a 14B model. Every scale-up event pays that cost.

Fix: network volumes with pre-loaded models

RunPod has network volumes — persistent NFS-backed storage that you can attach to workers at pod creation time. The key insight: provision the volume once, download all models into it, then mount it read-only on every worker.

Worker startup goes from “download 28GB” to “attach volume, start process” — roughly 15 seconds vs 8 minutes.

The automation:

  1. A provisioning script runs once per volume. It pulls every model from HuggingFace and CivitAI into the right ComfyUI directory structure.
  2. Workers declare the volume mount. On spin-up, models are already there.
  3. When a new model is added to the pipeline, re-run the provisioning script. No worker image changes needed.

Base image inheritance

With several different worker types (video gen, pose estimation, segmentation), the naive approach is one big image per pipeline. The problem: every shared dependency — CUDA version, Python environment, ComfyUI base — gets duplicated and diverges over time.

Instead, a base image owns:

  • CUDA and cuDNN
  • Python + pip dependencies shared across all workers
  • ComfyUI core
  • The entrypoint and health check logic

Each worker image does one FROM base:latest and adds only its specific custom nodes and config.

When CUDA needs updating or a shared dep changes, one push to base propagates to the entire fleet on next deploy. No drift.

What surprised me

ComfyUI’s API is workflow JSON, not a simple inference endpoint. Workers receive a full workflow graph, execute it node by node, and return outputs. This means the client constructs the entire pipeline — sampler settings, LoRA weights, conditioning — and the worker is a dumb executor. Debugging failures requires tracing through the graph.

ViTPose and YOLOv10 are fast enough that cold starts dominate their latency budget. For these smaller models, the volume pre-loading matters more than GPU choice.

Multi-LoRA video generation is memory-sensitive. Wan2.2-Animate 14B at full precision won’t fit on a 24GB card with two LoRAs loaded. You need either quantization or careful LoRA offloading between frames.

Current state

The fleet handles pose estimation, video segmentation, VAE decode, and multi-LoRA video generation as separate worker types behind a single job queue. Workers scale to zero between jobs. Cold start after scale-down is under 20 seconds.
