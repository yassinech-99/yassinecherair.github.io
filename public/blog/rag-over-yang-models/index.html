RAG over YANG models and vendor CLI docs for network automation

How we grounded an LLM's network device responses using hybrid BM25 + vector retrieval over YANG schemas and vendor documentation.

March 15, 2026

Open in harness → /?read=rag-over-yang-models

The grounding problem

An LLM roleplaying as a Cisco router will hallucinate output. Not because it doesn’t know the commands — it does, from training data — but because it doesn’t know the specific device state or the exact vendor variant for an output format.

A show ip ospf neighbor on IOS-XE looks slightly different from IOS. A show interface output on a Nexus device has different fields than on a Catalyst. Ansible playbooks often parse specific column positions. A hallucinated space breaks the parse.

We needed to ground every response in the actual vendor documentation.

The corpus

Two sources:

YANG models — machine-readable schemas published by Cisco, Juniper, and others that define the exact structure of every configuration and operational data tree. They’re precise but terse. Great for validating that a response has the right fields; less useful for generating realistic CLI output.

Vendor CLI docs — the actual command reference PDFs, converted to text. Verbose. They contain example outputs, which is what we actually needed for generation.

Both were chunked, embedded, and indexed. For YANG we kept the tree structure in the metadata — a query for bgp neighbor state could retrieve the parent bgp container and its children together.

Why hybrid retrieval

Pure vector search over CLI docs retrieves semantically similar content but can miss exact command names. show ip bgp summary and show bgp ipv4 unicast summary are semantically close but syntactically different — the wrong one in context produces a wrong response.

BM25 retrieves by exact term match. It catches the command string precisely but misses paraphrases and implicit context.

Hybrid (BM25 + vector, scores merged via RRF) got us the best of both: exact command matches ranked high, with semantic context filling in when the exact string wasn’t in the query.

In practice: ~80% output parity with real hardware on scripts the NetOps team wrote for production devices. Not perfect. Good enough to run automation validation before touching real hardware.

Context window management

A multi-step Ansible playbook sends many commands in sequence. Each response needs the session history — prior commands and outputs — to maintain device state (e.g., knowing that interface GigabitEthernet0/0 was entered means subsequent commands are in interface config mode).

Full history hits the context limit fast on longer playbooks. We added a summarization node: when history exceeds a threshold, a separate LLM call compresses it into a state summary. The summary preserves what matters — current mode, applied config, interface states — and drops the raw command/response pairs.

The tradeoff: the summary is a lossy compression. Occasionally a detail that mattered gets dropped. We tracked these cases and tuned the summarization prompt over time.

What we’d do differently

Finer-grained YANG chunking. We chunked by container node, but some containers are huge. Better: chunk at the leaf list level with parent path as metadata.

Per-vendor retrieval indices. We merged all vendors into one index. Cross-vendor contamination was a real source of errors — IOS-XE syntax leaking into Junos responses. Separate indices with routing by detected vendor in the query would clean this up.

Structured output validation. After generation, parse the CLI output against the YANG schema. Reject and regenerate if the structure doesn’t match. We designed this but ran out of runway before implementing it.
