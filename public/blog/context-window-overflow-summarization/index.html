Solving context window overflow in a stateful LLM agent

When your agent's conversation history grows faster than the context window — a summarization approach that preserves session state.

February 3, 2026

Open in harness → /?read=context-window-overflow-summarization

The problem with stateful agents

Most LLM agent demos are stateless: user sends a message, agent responds, done. Real workflows are different. A NetDevOps engineer running an Ansible playbook against an emulated device might send 40–60 commands in a single session. Each command’s output needs to be in context so the agent knows the current device state.

At around message 20, you hit the context limit. What then?

Option 1: sliding window

Keep only the last N messages. Simple. The problem: early messages often contain critical state. If you configured an interface in message 3 and ask about it in message 45, a sliding window that starts at message 30 produces a wrong answer — the agent thinks the interface was never configured.

For a network device emulator this is especially bad. The device is its state. Forgetting earlier config is equivalent to the device rebooting mid-session.

Option 2: summarization node

When the token count of the conversation history exceeds a threshold, trigger a summarization step:

  1. Pass the full history to a separate LLM call with a prompt focused on extracting device state.
  2. The summary captures: current CLI mode, applied configuration, interface states, routing table entries, any error conditions encountered.
  3. Replace the history with the summary. Subsequent messages get the summary as context instead of the raw transcript.

The summary prompt matters a lot. A generic “summarize this conversation” produces prose that’s hard for the agent to use. A structured prompt — “extract current device state in the format: mode / config / interfaces / routes” — produces something the agent can reason against reliably.

Implementation

We used LangChain’s ConversationSummaryMemory as a starting point, then customized the summary prompt heavily for the network domain. The standard prompt produces natural language summaries; we needed structured output that listed specific config state.

The summarization trigger was token-count based. We counted tokens before each LLM call and triggered summarization when we exceeded 60% of the context limit. That left headroom for the current request plus the response.

The tradeoff we accepted

Summarization is lossy. The raw transcript contains information the summary might drop. In testing, we found the main failure mode was losing the order of operations — the summary knew what was configured but occasionally lost when relative to other changes, which mattered for troubleshooting scenarios.

We logged every case where the agent’s response after summarization differed from what a full-context response would have been. Most differences were benign. A handful were significant enough to affect playbook output. We documented this as an accepted architectural tradeoff: the alternative (hitting the context limit and failing the session entirely) was worse.

Alternative we evaluated: external session storage

Instead of summarizing into the context window, store session state externally in Neo4j and retrieve relevant state on each query. This sidesteps the context limit entirely — you never need to fit the full history in the window.

We prototyped it. The retrieval approach worked well for config state (structured, queryable). It worked poorly for conversational flow — the agent needed to understand the sequence of what happened, not just the current state, to handle some error recovery scenarios.

The hybrid would be ideal: external storage for device state, in-context summary for session flow. We ran out of project runway before implementing it. The summarization approach was good enough to ship.

Lesson

Context window management is an architectural concern, not an implementation detail. Design for it before you need it. The shape of your data — structured state vs. conversational history — determines which approach fits. They’re not the same problem.
